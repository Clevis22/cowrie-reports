## Summary

The sensor logged 2,240 external sessions from 158 addresses between 01:06 UTC on 23 November and 01:06 UTC on 24 November. Most connected and did nothing else: 1,675 sessions ran no commands. Of the 565 that did, 551 executed the same GPU and host inventory, and 6,500 commands were recorded in total. Two Netherlands addresses in AS198364 sent 1,108 sessions between them, including a three-hour stretch that produced 1,363 sessions. No external uploads were captured.

## What the bots did

`connect-only` explains 1,675 sessions, `gpu-recon` 551, `host-recon` 9, `other-command` 3 and `payload-fetch` 2. The GPU script is the day's defining behaviour, and almost every session that ran anything ran it:

- `uname -s -v -n -r -m`
- `nproc`
- `lspci | egrep VGA && lspci | grep 3D`
- `lscpu | egrep "Model name:" | cut -d ' ' -f 14-`
- `nvidia-smi -q | grep "Product Name"`
- `curl ipinfo.io/org`

A second block, run 21 times, cleans the host before anything else: `crontab -r ; rm -rf /var/tmp/.* /var/tmp/* /tmp/.* /tmp/* ; … pkill -9 xmrig … pkill -9 cpuminer … pkill -9 minerd … pkill -9 ccminer …`. It removes cron entries and kills four named miner processes, which reads as an attempt to evict competing mining software. That is an inference from the command, not proof it succeeded on a real host.

Collecting GPU product names, VGA and 3D devices, CPU model, core count, uptime and the host's own organisation is consistent with selecting machines for mining. This is inferred from the command set; the sensor reports emulated output, so none of the returned values is hardware evidence.

## Sessions worth reading

- `112.197.2.116`, port 22, session `7b5b00beefaa`, 826 events in 35 seconds, login `root/ubuntu0` accepted. It ran a shorter, custom check: `cat /proc/cpuinfo | grep 'model name' | head -1`, `nvidia-smi --query-gpu=name --format=csv,noheader`, `netstat -tulpn 2>/dev/null | grep LISTEN`, then wrote and removed `/tmp/.ametist` and read `/etc/network/interfaces`. No upload, and one hybrid reply fell back to the static responder.
- `109.160.32.147`, port 22, session `1fa41ffdaa56`, 86 events over five minutes, login `root/122112` accepted. It ran the full inventory, the crontab and miner-kill block quoted above, and `echo 122112 > /tmp/d.log`. The same address opened 522 sessions in the window, all with the same client fingerprint.
- `109.160.32.115`, port 22, session `13042577e1e0`, 86 events, login `root/26262626` accepted. Ten seconds later the same address opened `68f3423a798d` with `ubuntu/123456789` accepted and ran the identical script. Two credential pairs taken from the honeypot's list, back to back, no delay.

## Method and limits

Window: 2026-11-23T01:06:01Z to 2026-11-24T01:06:01Z, 24 hours, taken from the Cowrie hybrid sensor's compressed segments in the collector's Drive folder. Loopback and harness-marked sessions are excluded from external counts; 252 such sessions and 10 addresses were set aside. A successful login is against the honeypot's own credential list, not a real host. A captured hash proves capture, not execution. Emulated shell output and LLM replies are not evidence of hardware or network state.
